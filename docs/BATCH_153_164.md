这 12 轮的主线：**从“加能力”转向“证明失败时的行为”**。大部分轮次在测“坏的时候会怎样”，而且**三次尝试里两次失败**——失败的过程也都留在文档里。

### 2) 修掉一个真正的“谎报成功”

`SendFlow.sendWithRecovery` 原来只要 `sendDispatch` **没抛异常**就当成功，但内核在结果未确定时返回 `status=unknown / settled=false` → 界面会把**未确定**当成**已发送**。现在显式判断 `status == accepted && settled`，否则按 `SEND_REJECTED` / `UNKNOWN_RESULT` 如实失败，并提示“必须按 SubmissionId 对账，不要重发”。

### 3) 故障注入：能造出来的才测得了

| 轮次 | 故障 | 结果 |
| --- | --- | --- |
| R-280 | 杀节点 | ✅ PASS（如实 `NODE_UNAVAILABLE`） |
| R-281 | 网络分区（握手成功无应答） | ✅ PASS（26.3s 后如实失败） |
| R-288 | 数据库只读 | ✅ PASS（节点 `STORAGE_FAILURE` 启动失败，客户端如实失败） |
| R-285 | 失败窗口（同进程两次） | ❌ 未做成（移除 phase D） |
| R-287 | 拉取路径分区 | ❌ 未做成（游标未初始化） |

**经验**：故障能不能测，取决于它能不能被**可逆地**造出来。只读属性是干净开关；让进程在运行中死掉、让游标凭空存在都要改产品面。
